Working architecture

Family Homelab

Local infrastructure designed around recovery, not novelty

A family-scale environment for storage, media, home automation, identity, development, observability, and local AI—consolidated around systems that can be understood and recovered when something fails.

The operating requirement

A homelab can be a perpetual experiment. Family infrastructure cannot. Media, photos, home automation, documents, credentials, and remote access have users who reasonably expect them to work without caring which container, host, or identity protocol makes that happen.

The architecture therefore favors a boring control path, explicit ownership, portable data, and recoverable configuration. New tools are useful only when they reduce a real operating burden or create a capability worth maintaining.

Current architecture

  • Stable consolidation host Unraid provides storage and the primary container runtime. Work that had been spread across a less reliable mini PC is being consolidated so an auxiliary machine is not the sole control point for critical jobs.
  • Containerized home automation Home Assistant, Zigbee, Z-Wave, and MQTT run as separable services. Radio state, controller backups, security keys, and application configuration are treated as distinct recovery concerns.
  • Private access boundary pfSense provides the network boundary and HAProxy provides reverse proxying. Services are not deliberately exposed to the public internet; Tailscale supplies authenticated remote access.
  • Identity and credentials Bitwarden holds human credentials. Authentik and OIDC are the application identity direction, reducing separate credentials without trying to make one identity system control every possible recovery path.
  • Observable services Prometheus, Grafana, and Loki provide the basis for metrics, dashboards, and logs. Observability is being developed alongside consolidation rather than treated as proof that silent failure has already been eliminated.
  • Portable configuration and off-site recovery Docker Compose configuration is moving toward Git-managed source. Restic with Backrest and Backblaze B2 form the backup direction, with restore verification remaining the meaningful measure of completion.

Design principles

  • Portable roots Data, recovery material, and configuration should outlive a particular application or provider.
  • Controlled exposure Remote access does not require turning every internal service into a public web application.
  • Replaceable services Containers and hosts should be reconstructable wherever practical; durable state receives different treatment.
  • Operational honesty A dashboard is not a backup, a scheduled job is not a verified restore, and “self-hosted” does not automatically mean resilient.

Lessons from consolidation

The most important architectural change was not adopting a new platform. It was recognizing that a quiet, headless mini PC could fail in ways that were easy to miss and therefore should not be the sole scheduler or control point for backups and family-critical services.

The Home Assistant migration reinforced a related lesson: a service is not fully described by its container. Z-Wave network identity, controller nonvolatile memory, security keys, device mappings, broker state, and application configuration each have different recovery requirements. A successful architecture makes those boundaries explicit before the failure.

What is not finished

This is a working architecture, not a claim of completed operational maturity. Backup coverage and restore drills need to be documented, the Git-managed service inventory needs a clean public-safe view, identity adoption is still uneven, and secrets management is moving toward a more explicit machine-credential workflow.

Publication boundary

A future detailed version can show logical topology, service responsibilities, backup classes, and representative configuration. It will not publish private addresses, credentials, recovery material, externally useful attack paths, or family data.

System areas

  • Storage and containers
  • Network boundary and remote access
  • Identity and credentials
  • Home automation
  • Media and family services
  • Metrics, logs, and dashboards
  • Backup and off-site recovery
  • Local development and AI

Status language is deliberate: “current,” “direction,” and “remaining” distinguish deployed capability from intended architecture.
